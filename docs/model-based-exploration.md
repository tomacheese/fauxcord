# Model Based API Exploration

Fauxcord includes a seeded explorer for combinations of Guild, Channel, and
Message operations. It uses the production app assembly on an ephemeral local
port, an in-memory SQLite database, and a local Gateway WebSocket. It does not
connect to Discord or use a real bot token.

## Run it

The short seeded scenario is part of the regular test suite:

```bash
pnpm test
pnpm fuzz:short
```

Run a longer exploration with an explicit unsigned 32-bit seed and operation
count:

```bash
pnpm fuzz --seed 317 --steps 5000
```

Run the full public API coverage sweep with a reproducible operation order:

```bash
pnpm fuzz:full --seed 317
```

This sweep exercises every success branch in `spec/manifest.ts` against a fresh
server built through the production app assembly, then runs each branch's
response and state assertions. It also covers Fauxcord's non-OpenAPI guild
deletion route and complete OAuth2 authorization-code and client-credentials
flows, including token revocation. A connected Gateway client also verifies all
16 dispatch event types emitted by Fauxcord's resource bus, with increasing
sequence numbers and resource identity fields. The seed changes operation order
without reducing coverage. `_test` and `_mock` routes provide local test
controls, health checks, and attachment serving rather than Discord-facing API
behavior.

The same seed and step count generate the same symbolic operations and
validation checks. Snowflake IDs and timestamps are generated by Fauxcord at
runtime; reports preserve their observed values, while the checker compares
modeled properties rather than timestamp text or generated IDs.

## Findings and replay

When an invariant fails, the command exits with status 1 and writes a JSON
report under `.fauxcord-exploration/`. Pass `--out <path>` to choose a report
path. Existing files are not overwritten. The report includes the seed, all
generated operations and inputs, each HTTP request and response, the expected
invariant, the actual mismatch, and Gateway frames observed before the finding.

The runner also attempts delta debugging. It removes chunks of operations and
replays each candidate from a fresh test server. Operations whose resource
creation was removed are skipped during replay, so a shorter scenario is kept
only when it still reports the same invariant. The report stores both the
original and minimized operation lists and the minimized trace. Use
`--no-minimize` for a faster first pass.

Replay a reported scenario by using its seed and original step count:

```bash
pnpm fuzz --seed 317 --steps 5000
```

For exact replay of an already minimized report, copy its `minimized.operations`
array into a focused test that calls `runModelScenario`. This preserves the
symbolic resource references and payload values while creating fresh local
IDs.

## Explorer model

The short randomized generator tracks active and deleted Channels and Messages.
Its operations include channel creation, lookup, listing, and deletion; message creation,
lookup, editing, listing, and deletion; reaction and pin transitions; repeated
operations; cross-channel references; malformed emoji encoding; rejected
message lengths; and the 2,000-character content boundary.

Checks cover response status and body fields, read-after-write behavior,
channel/message relationship constraints, channel lists, test-control message
state, SQLite message/reaction/pin rows and delete cascades, and the matching
Gateway dispatch for state-changing operations. Expected Discord error codes
and response shapes are cross-checked against `spec/manifest.ts`,
`spec/openapi.json`, and the route tests. Cross-resource isolation invariants
follow the channel-scoped REST paths in Discord's [Message API
documentation](https://github.com/discord/discord-api-docs/blob/main/developers/resources/message.mdx).
The full sweep runs the 246 OpenAPI endpoint/method pairs in the manifest and
all 258 success branches, plus the supplemental public API and Gateway
scenarios. The existing `compat/` suite remains the high-level Discord-library compatibility
check; this explorer directly exercises Fauxcord's local HTTP and Gateway
interfaces.

To add an operation, extend `ModelOperation`, add its state transition to
`generateModelOperations`, and implement its HTTP request and assertions in
`executeOperation`. Include both a valid state transition and any relevant
stale-resource, duplicate, cross-resource, or boundary case. Add a focused
regression scenario to `model-based-explorer.test.ts` when the operation adds a
new invariant.

## Investigate a finding

1. Replay the seed and inspect the report's operation, request, expected value,
   response, Gateway payload, and database evidence.
2. Decide whether the mismatch comes from Fauxcord, the model or checker, test
   setup, or the runtime environment. Treat the report as a lead, not as proof
   that Fauxcord violates Discord behavior.
3. Confirm the expected behavior in the relevant OpenAPI entry, existing
   contract test, route test, or another authoritative Discord specification.
   If the specification is silent, record that uncertainty and avoid asserting
   an unsupported Discord guarantee.
4. Reproduce the operation in a focused test. Fix Fauxcord only after the
   mismatch is confirmed, and add a regression assertion for the corrected
   behavior.

The full sweep covers implemented threads, attachments, webhooks, interactions,
roles/permissions, and other manifest-backed API features through their
dedicated contract fixtures and state assertions. The randomized multi-step
state model does not combine every one of those resource families into long
cross-feature sequences, and the explorer does not model external services.

The mutation self-test injects three defects only at the isolated harness
boundary: a corrupted create response, a successful deletion response while
state remains, and a dropped Gateway event. These mutations verify response,
state, and Gateway checkers; they do not alter Fauxcord source or persist in
the final application.
